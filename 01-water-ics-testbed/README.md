# 01 · 供水管网工控安全测试台

> 一套用于验证「水务监测告警逻辑能否识别数据篡改」的可复现实验环境。
> 仿真底座：`Critical-Infrastructure-Systems-Lab/DHALSIM`（MIT）。

**状态**：方案与部署手册完成，待上机实跑（编写环境为 Windows，缺 Mininet / root / netfilter）

## 我要解决什么

水务行业正在把 SCADA、管网模型、调度系统连成一张网，但较少有人回答一个问题：
**如果传感器读数在传输路上被改了，调度侧看得出来吗？**

要回答它，需要能同时给出「真实物理量」和「系统看到的量」的实验环境。本测试台就是为了产出这两份对照数据：

| 产物 | 含义 | 用途 |
|---|---|---|
| `ground_truth.csv` | 仿真中的真实物理量（含攻击标记） | 正样本 / 真值 |
| `scada_values.csv` | 调度侧在网络上实际收到的值 | 观测值 |
| `*.pcap` | 各节点与攻击者报文 | 事后取证与复现 |

两者之差就是攻击效果。**这套对照关系是测试台的核心价值：它让异常检测的训练数据可以自动生成，不需要人工标注。**

## 方案边界

**做什么**
- 安全评估基准：用真实管网 `.inp` 复现「数据被篡改但不报警」的场景，检验告警规则是否有效
- 标注数据生成：为异常/攻击检测模型提供带真值的训练与测试样本
- 培训与认知：让人直观看到「工控协议为什么缺少完整性保护」

**不做什么**
- 不做数字孪生运行时：它同步的是水力模型，不是真实水厂；无 historian、无水质参数、采样率不可配
- 不做甲方内网交付：要 root、要内核 netfilter、要源码编译 Mininet，部署门槛不适合生产环境
- 不替代 EPANET 生态自研的水力计算：它只是 EPANET 的编排层

## 五个关键判断

1. **进程间同步靠单个 SQLite 文件**（5 张表），靠重试硬扛写锁。做实验够用，但拓扑一大就是瓶颈，不能当工程方案。
2. **选 `epynet` 后端会删掉 `.inp` 的 `[CONTROLS]`**，控制改由 PLC 承担 —— 拿它做「EPANET 原生控制 vs PLC 控制」对比实验时，口径会被破坏，必须留档 `*_processed.inp`。
3. **`ground_truth.csv` 与 `scada_values.csv` 的对照关系是全部价值所在**，没有这两份数据，实验就只是看动画。
4. **隐蔽篡改（concealment）才是真实威胁形态**：先改值、再把其余测点伪装成正常，目标是「让系统别报警」而不是「让系统报错」。本方案的验证重点放在这一类。
5. **传感器只有液位 / 压力 / 流量三类，没有水质**；采样率不可配，与仿真步长同频。这决定了本测试台**不适合**验证水质异常类检测。
