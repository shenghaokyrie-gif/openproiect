# 供水管网工控安全测试台 · 实施方案

> **本方案要解决的问题**：在不接入生产系统的前提下，构造一套可复现的「传感器数据被篡改、但调度侧看不出异常」的实验环境，
> 用来回答一个具体问题——现有的告警与异常检测逻辑，到底能不能抓住这类篡改。
>
> 仿真底座选用 `Critical-Infrastructure-Systems-Lab/DHALSIM`（MIT）。本方案做的是**选型、场景定义、参数取舍与验收设计**，
> 不改写其内核，也不把它的能力当成自己的成果。凡是我没有亲自跑通的环节，见 §10。

---

## 0. 底座定性（这个判断决定后面所有取舍）

**DHALSIM 是一个把「供水管网水力仿真」和「工控网络仿真」缝在一起的联合仿真测试床**：
物理侧跑 EPANET（WNTR / epynet 两种绑定），网络侧跑 Mininet + ENIP/CIP，
两边靠一个 SQLite 文件做同步总线，最终产出「物理真值 CSV」和「SCADA 看到的 CSV」两份对照数据。

**它不是产品，是实验台。** 入口 `sudo dhalsim xxx.yaml`，要 root、要 Linux 内核 netfilter、要 Mininet，
没有服务化接口，没上 PyPI，版本停在 1.1.1。

正因为它是实验台而不是运行时，我的方案边界也就定了：**只做实验环境，不做系统集成；只出验证结论，不承诺上线。**

---

## 1. 我为什么要建这套测试台

我的关注点是智慧水务。这个领域有个结构性问题：
水力模型（EPANET）和业务系统（SCADA / 调度 / 营收）之间，开源社区几乎是断开的。
EPANET 那条线的工具链很成熟，但**没人管「数据从模型到系统这一路会不会被改」**。

DHALSIM 恰好是这个缺口的样本：它承认「SCADA 看到的值」和「真实物理值」是两个东西，
并且把两者都记录下来。这个视角对我有用——**它把「传感器数据」从「事实」降级成「声明」**。

---

## 2. 它到底是什么：三层，别混着看

| 层 | 用什么实现 | 我的理解 |
|---|---|---|
| 物理层 | WNTR 或 epynet（都是 EPANET 的 Python 绑定） | 真的在解水力方程，产出压力/流量/液位 |
| 网络层 | Mininet + Open vSwitch + `tc` | 真的在跑 TCP 报文，有 IP/MAC/网关 |
| 同步 + 数据层 | **单个 SQLite 文件** | 进程间总线，也是全项目最脆弱的地方 |

关键认知：**它没有 Kafka、没有 MQTT、没有 REST、没有 ZeroMQ。**
我一开始以为这种「工控数字孪生」肯定挂消息中间件，实际全项目就一个 `.db` 文件。
进程间的「共享内存」是 SQLite 表 `plant(name, pid, value)`，
「全局时钟」是 `master_time(id, time)` 单行表，「握手」是 `sync(name, flag)` 状态机。

这个设计我给的评价是：**科研够用，工程上不能碰。**
因为它靠 `DB_TRIES=10` 次重试 + 10~100ms 随机退避硬扛 SQLite 的 writer 锁，
拓扑一大（ctown / ky15，2880 迭代）就变成性能瓶颈，代码里到处躺着 `#time.sleep(0.3)` 这种实验性注释。

## 3. 一次仿真是怎么跑起来的

我把它的同步时序抄成下面这样，这是我理解它最关键的一段：

```
Runner.run()                                    # dhalsim/command_line.py
  ├─ ConfigParser 生成 intermediate.yaml         # 物化场景
  ├─ DatabaseInitializer.drop() / .write()       # 重建 SQLite
  ├─ pkill cppo.server.enip ; mn -c              # 清理上一轮残留
  └─ Popen(["python3", ".../python2/automatic_run.py", intermediate.yaml])
        └─ GeneralCPS(MiniCPS)
             ├─ Mininet(topo=SimpleTopo|ComplexTopo) .start()
             ├─ topo.setup_network()  → 拉起 plant / plc×N / scada / attacker
             └─ 每个子进程都只吃同一个 intermediate.yaml
```

每个 hydraulic timestep 的握手（`physical_process.py` 的 `simulate_with_epynet()`）：

```
等所有 PLC ready(1)      → set_sync(2)      # 放行，PLC 可以收远端值
等所有 PLC ready(3)      → update_actuators()   # 从 DB 读回执行器状态
                        → wn.simulate_step(...) # 物理推进一步
                        → 物理量写回 DB
                        → set_sync(0)           # 交还控制权
                        → REPLACE INTO master_time
```

我从中读出的三个事实：

1. **1 iteration = 1 个 hydraulic timestep**，时钟是迭代计数，不是墙钟。
2. **它是保守同步**：每一轮所有角色都要会齐，谁也跑不快。轮询间隔硬编码 5ms。
3. **既不是实时，也没有固定倍速**。实际快慢取决于 Mininet 里 ENIP 往返 + SQLite 争用。
   它没有 PTP、没有 RTOS、没有离散事件调度器——「事件触发」其实是每轮轮询比较条件。

⚠️ 还有一点很坑：**epynet 内部会跳步**。`simulate_step` 可能推进多个子步，
DHALSIM 只把跨越 hydraulic_timestep 的那些计入 `master_time`，中间子步不记录。
所以拿它的 ground_truth 做时序对齐时要小心。

## 4. 场景是怎么定义的

最少 3 个文件，缺一不可：

```
xxx.inp              # EPANET 管网（拓扑/管径/需水/[CONTROLS]）
xxx_config.yaml      # 实验参数
xxx_plcs.yaml        # 几台 PLC，各自管哪些 sensor/actuator
```

我实际记住的是**中间层**：`ConfigParser` 会把这三个文件揉成一个 `intermediate.yaml`。
所有子进程读的都是 intermediate，不是原始 config。这层物化很有用——它就是「可复现实验」的载体。

intermediate 里除了我的配置，还会被自动补全一堆网络编址字段：
`local_ip / public_ip / mac / gateway_name / gateway_ip / gateway_inbound_mac /
gateway_outbound_mac / provider_ip / switch_name`。
看到这些字段我才明白：**ARP 欺骗所需的地址是框架自己分配的**，不是我自己配的。

拓扑二选一：
- `simple`：所有 PLC 和 SCADA 在同一局域网，共用 router；
- `complex`：每台各有独立 switch + router，走公网 IP 连中心 —— 做 MITM 更真实，示例全用它。

`.inp` 不用自己造，仓库自带 anytown(11.8K) / ctown(114K) / minitown(21.6K) / ky13-15(143–260K)，
都是标准 EPANET INP。但**只支持简单 `[CONTROLS]`**。

## 5. 传感器与执行器：能力边界比宣传窄

我按「能测什么」列了一遍，结果很朴素：

| 传感器 | 写法（直接用 `.inp` 里的对象名） |
|---|---|
| Tank level | `T41` |
| Junction pressure | `Junction5` |
| Valve flow | `V3F`（阀名 + F） |
| Pump flow | `P2F`（泵名 + F） |

**没有水质传感器。** 文档和代码里只有 level / pressure / flow 三种物理量，
氯、浊度、pH 这些一概没有。对水务来说这是明显的功能缺口——水质是二次污染和投诉的主要来源。

执行器只有两种：valve status、pump status（open/closed）。**泵速只有 epynet 路径支持**，
走 WNTR 会直接抛 `InvalidControlValue`。

噪声：`noise_scale`，就是加在 PLC 上报值上的**高斯噪声尺度**，默认 0（干净数据）。
示例里 WADI 用了 0.25。

**采样频率没有独立参数**——它和仿真迭代同频。PLC 侧缓存刷新是硬编码 `PLC_CACHE_UPDATE_TIME = 0.05` 秒。
所以「采样率」这件事在 DHALSIM 里不可配，这也是它离真实 SCADA 最远的地方之一
（真实系统里传感器、PLC、SCADA 三层周期各不相同）。

## 6. 攻击模型：我把它拆成三条线

这是我读它花时间最多的地方。别被 `doc/attacks.rst` 那 28KB 吓到，本质就三类：

### 线一：设备攻击 `device_attacks` —— 直接改执行器

```yaml
device_attacks:
  - name: V_ER2i_attack
    trigger: {type: time, start: 125, end: 375}
    actuator: V_ER2i
    command: closed
```

本质是「控制器输出被篡改」，通过 PLC 自己的 `set_tag()` 落地，链路上看不出异常。
触发条件 4 种：`time` / `below` / `above` / `between`（后者带 sensor 条件）。

### 线二：网络攻击 `network_attacks` —— 改报文

`type` 有 `mitm` / `naive_mitm` / `simple_dos` / `concealment_mitm`，
还有几个实现存在但示例里没出现的（`replay_mitm`、`black_box_concealment` 等）。

实现手法我核过，很"朴素但有效"：
- Scapy 做**双向 ARP 欺骗**（`launch_arp_poison` / `spoof_arp_cache` / `restore_arp`）把流量牵过来；
- **直接改报文最后 4 字节**，`struct.unpack('<f', raw[-4:])` —— 针对 CIP 里的 32-bit REAL；
- 自研 ENIP/CIP 协议解析器（约 34KB）用来定位要改的 tag；
- 或者用 Linux **NFQUEUE** 在用户态拦截改写。

**最阴的是 `concealment_mitm`**：不只是改值，还要把被篡改的量在 SCADA 视角伪装成合理值
（`concealment_data` 里给正常 tag 配正常值），甚至用 Keras 生成模型生成"看起来正常"的数据。
这个思路我认为比单纯的 MITM 更接近真实威胁——**攻击者的目标不是让系统报错，是让系统别报错。**

### 线三：网络事件 `network_events` —— 不是攻击，只是链路变差

```yaml
network_events:
  - name: link_loss
    type: packet_loss
    target: PLC1
    trigger: {type: time, start: 648, end: 792}
    value: 25
```

用 `tc` 实现，value 是丢包百分比。**文档只承诺 `packet_loss` 一种**，
虽然代码里有 `network_delay` 和 `delay_and_loss` 的实现文件。
这个区别很重要：做实验时如果引用了 `network_delay`，属于超出文档承诺范围。

## 7. 可观测性：这才是我真正想要的东西

跑完一轮，产物是：

- `ground_truth.csv` —— EPANET 里的**真实**物理量（带 attack 列）
- `scada_values.csv` —— SCADA **在网络上看到**的值
- 每台 PLC / 攻击者 / SCADA 各一个 `.pcap`

**两者的差 = 攻击效果。** 这句话是整套设计的核心。

我认为这是 DHALSIM 对我最大的价值：它给了"标注数据"的生成方式。
如果我以后要做「基于数据的水务异常/攻击检测」，正样本（真实物理状态）和负样本（被篡改的观测）
是天然对齐的——不需要人工标注。这条线我记下来了。

一个坑：**`scada_values.csv` 只含 PLCs YAML 里声明过的变量**。
我在 YAML 里漏声明一个测点，它就不会出现在结果里，而且不会报错。

## 8. 我核对出来的坑

我把它们分成两类，因为性质不同。

### 8.1 仓库文档自相矛盾（要按代码走，别按文档走）

| 矛盾点 | 实情 |
|---|---|
| `README` 说 Ubuntu **20.04**，`doc/installation.rst` 说 **22.04** | 两处不一致，install.sh 里读到了版本号但没用来分支 |
| `doc/user_guide.rst` 把 WADI 列为可用示例，但 `examples/wadi_topology/readme.md` 说 **v0.6.0 起已不支持**、仅留作教学 | 以 readme 为准，**WADI 别用** |
| 文档说 `simulator` 默认 `wntr` | 但**所有 5 个示例都用 `epynet`** |
| `requirements.txt` 只有 3 行 | 真正安装靠 `install.sh`，别信 requirements |

### 8.2 代码层面的硬事实（我认为最需要提前知道的）

1. **走 epynet 会改写我的 `.inp`**：`remove_controls_from_inp_file()` 把 `[CONTROLS]` 整段删掉，
   另存 `*_processed.inp`，控制逻辑改由 PLC 承担。
   → 后果：**原始 EPANET 控制规则失效**。如果我想对比「EPANET 原生控制」和「DHALSIM PLC 控制」，口径直接被破坏。
2. **WNTR 后端是残缺的**：泵速不支持（抛 `InvalidControlValue`）；初始 junction 压力直接写 0，
   代码里还留着 `# toDo: Check in wntr 0.4.2...`。
3. **依赖锁死且极重**：`tensorflow==2.13.1` + `keras==2.13.1` + `numpy==1.24.3` 是**必装**（在 install_requires 里），
   但只被 concealment 类攻击用到。TF 2.13 只到 py3.11 左右 → **Python 环境窗口非常窄**。
4. **`python2/` 目录名是误导**：里面全是 Python 3 代码，`command_line.py` 明确用 `python3` 拉起。
5. **从源码编译 Mininet 2.3.1b4 + 三个无版本锁的 Git fork**（`afmurillo/minicps`、
   `afmurillo/DHALSIM-epynet`、`kti/python-netfilterqueue`）。上游一动，安装就挂。
6. **仓库很重**：`training_data.csv` 79MB、`concealed_values.txt` 3.6MB。别随手全量 clone。
7. **同一节点叠两个网络攻击，文档明说「行为未测」**。做多攻击实验要自己兜底。

## 9. 我的取舍

### 我会用它做的

- **当安全评估基准**：拿到一个水司的管网 `.inp`（EPANET 格式），我可以低成本复现
  「传感器数据被篡改但不报警」的场景，去验证我的检测逻辑是否真的能抓到。
- **当异常检测的数据生成器**：ground_truth vs scada_values 天然对齐，省掉人工标注。
  这条比它本身作为仿真器更有价值。
- **当攻击面的教科书**：ARP 欺骗 + CIP 报文定点篡改 + NFQUEUE 这一整套组合，
  是理解「工控协议为什么没有完整性保护」的最短路径。

### 我不会用它做的

- **不会当数字孪生运行时**。它同步的是 EPANET 模型，不是真实水厂；
  没有 historian、没有回放、没有水质、没有采样率配置、没有实时保证。
- **不会当产品交付给水司**。要 root + 内核模块 + 源码编译 Mininet，
  这个部署门槛在甲方内网是不可能落的。
- **不会用它替代 EPANET 生态自研的水力计算**。它只是 EPANET 的编排者，
  而且 epynet 那条路还会改写我的 `.inp`。

**结论：把它当「攻击样例与标注数据的来源」，不要当平台。**

## 10. 我没验证的部分（诚实清单）

本方案的设计判断基于**源码与文档核对**，**尚未在目标机上跑通**。原因：
本机是 Windows，DHALSIM 要 Linux + root + 内核 netfilter + Mininet，装不了。

因此以下几点我没有第一手证据，落地前必须自己验：

1. `install.sh` 在当前 Ubuntu 版本上到底能不能一次装通（依赖里三个 fork 都无版本锁）。
2. `scada_values.csv` 的实际列定义和轮询时序（`generic_scada.py` 16KB 我没逐行读）。
3. `type:` 字符串到攻击实现类的**完整映射**（推测由 `automatic_attacker.py` 分发，未确认）。
   这意味着我不确定 `naive_mitm` 和 `mitm` 的实际差别到底在哪。
4. `network_delay` / `delay_and_loss` 是否真能用（文档只承诺 `packet_loss`）。
5. 大拓扑（ctown / ky15，2880 迭代）下的实际耗时和 SQLite 争用情况。
6. 是否有水质传感器——我判定为不支持，但没找到明文声明。
7. 论文 II / III 的发表年份（README 只给了 DOI）。
